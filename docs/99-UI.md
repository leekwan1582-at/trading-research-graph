# Research Control Center: UI Proposal

A local-first control panel for submitting research requests, running repository tests, and executing approved agent stages with visible evidence and lineage.

**Status:** Proposed design, not an implemented or tested application. The repository and earlier downloadable packages have not been inspected. Package names and state fields below follow the conversation and must be checked against the actual code before implementation.

## Recommended first version

Build a **Streamlit interface backed by a small FastAPI control service, a separate Python worker, and a local SQLite database**. Keep existing request, supervisor, and data packages as the execution engine. The UI should replace repetitive terminal operations, not rewrite validated quantitative logic.

Use explicit buttons and forms rather than a conversational chatbot as the primary interface. Streamlit supports forms that submit related inputs together, but its ordinary interaction model reruns scripts; session state is not durable job storage. Therefore, job submission must go through the service, and jobs must continue independently of browser tabs. [docs.streamlit](https://docs.streamlit.io/develop/concepts/architecture/forms)

Initial operating assumptions: single user, local WSL, one active execution job, trusted repository, no live broker actions, and no automatic code changes. These are defaults for the proposal, not requirements already confirmed by the user.

### Options

| Approach | Evidence and fit | Recommendation |
|---|---|---|
| Streamlit + control API + worker | Python-oriented forms and tables; forms batch input, while session state remains session-scoped. [docs.streamlit](https://docs.streamlit.io/develop/concepts/architecture/forms) | Recommended MVP: concentrate effort on reliable execution and evidence. |
| Custom browser frontend + control API + worker | Proposed option for a richer node inspector, keyboard interactions, and a highly tailored layout. | Consider after the execution contract is stable; not necessary to automate the present workflow. |
| LangSmith Studio | Supports graph visualization, agent execution, intermediate-state inspection, and thread debugging through Agent Server. [docs.langchain](https://docs.langchain.com/langsmith/studio) | Optional developer debugger alongside the control panel, not a replacement for the proposed repository-test and artifact gates. |

No framework price, development-time estimate, or subscription assumption is required for this recommendation.

## First usable workflow

The primary action is **Verify & Run to Selected Stage**:

1. Select the configured repository and environment profile.
2. Choose a registered request file or edit a draft in the form.
3. Select an available target: Validate Request, Plan Only, or Prepare Data.
4. Review the resolved instrument universe, dates, snapshot, execution scope, and fixture/real-data label.
5. Submit once; the backend creates a durable job and returns its ID.
6. Preflight verifies imports, contract versions, paths, available stages, and environment compatibility.
7. Run required pytest suites against the selected source snapshot.
8. If all gates pass, execute only the selected, explicitly authorized scope.
9. Inspect the actual state, logs, test evidence, and published artifact references.
10. Clone a completed job to start a new attempt; never overwrite the historical run.

**Stop on failure.** A failed request, failing suite, missing suite, incompatible package, stale evidence, or mismatched instrument/snapshot prevents downstream execution. The UI explains the block rather than suggesting that the user disable the check.

For the first release, “automation” means reliable tests and execution of existing code. It does not mean generating agents, editing source, fixing tests, installing packages, or trading autonomously.

## Keep three kinds of status

Avoid one ambiguous green “success” badge.

| Status dimension | Proposed values | Meaning |
|---|---|---|
| Control-plane job lifecycle | queued, running, cancel_requested, succeeded, failed, cancelled, timed_out, orphaned | Whether the requested job completed operationally |
| Domain pipeline state | request_validated, queued, planned, data_ready, plus later stage states | What the existing packages actually produced |
| Research acceptance | not_evaluated, accepted, rejected | Whether the statistical/research criteria were evaluated and met |

A job can succeed with domain status `planned` while research acceptance remains `not_evaluated`. A fixture-based Data run can verify mechanics without validating a profitable strategy.

Show individual test outcomes separately from the aggregate suite and gate outcomes. For example, “Suite completed; required coverage missing” is different from “Tests failed.”

## Test and execution modes

| Mode | What the backend does | Expected boundary |
|---|---|---|
| Tests Only | Run the selected allowlisted suites; do not submit a research execution | Test evidence only; no agent artifacts outside test scratch space |
| Validate Request | Invoke the existing intake validator | Accepted receipt or structured rejection |
| Plan Only | Intake → handoff → supervisor | `planned`; iteration remains zero; no Data execution |
| Prepare Data | Intake → supervisor → authorized Data adapter | `data_ready` only after verified artifact publication |
| Full Research | Not implemented in the MVP | Disabled until later agents, budgets, and acceptance gates exist |

For Prepare Data, run intake, supervisor, and data regression suites plus the end-to-end integration checks registered for that scope. Initially, prefer the complete registered regression set over clever change-based test selection.

**Do not assume earlier example fixtures are compatible.** An ES request must not be silently paired with a BTCUSDT snapshot. Contract, instrument mapping, date coverage, strategy specification, and snapshot identity must agree. A deliberately incompatible request should show a useful rejection.

### Gate policy

Store machine-readable test reports using pytest's JUnit XML output, together with the unmodified process exit code and a runner-generated summary. Do not infer success by searching console text for “passed.” [docs.pytest](https://docs.pytest.org/en/stable/how-to/output.html)

Proposed gate requirements:

- The configured suite exists and completes before its timeout.
- The selected interpreter and environment match the intended execution profile.
- Exit code is zero and reports are present and parseable.
- Expected required tests were collected and actually executed; zero collected tests is a block, not success. Pytest identifies no collection with exit code 5. [docs.pytest](https://docs.pytest.org/en/stable/reference/exit-codes.html)
- Required tests are not skipped or only xfailed. An explicitly documented exception must remain visible in policy and history.
- Source, environment, request, dataset, policy, and execution fingerprints still match the evidence.
- Selected node prerequisites and execution permissions are satisfied.

A filtered rerun of a failed test is useful diagnostics but does not replace the complete evidence needed for the execution gate. Do not reuse old green badges after a code or input change.

## Architecture

```text
Browser / Streamlit UI
        |
        | submit / inspect / cancel
        v
FastAPI control service
        |
        +---- SQLite: jobs, attempts, events, evidence, artifact index
        |
        v
Dedicated single worker
        |
        +---- allowlisted pytest subprocesses
        |
        +---- intake / supervisor / Data adapters
        |
        +---- LangGraph execution where applicable
        |
        v
Run-specific scratch space ---> verified immutable artifact store
```

The FastAPI service validates submissions, stores durable jobs, serves inspection data, and enforces policy. The worker owns execution, leases, heartbeat updates, process supervision, and final outcome publication.

Do not run future calibration/backtests synchronously in the UI or HTTP handler. FastAPI's documentation distinguishes small in-process background tasks from heavier work that benefits from separate process/job infrastructure. [fastapi.tiangolo](https://fastapi.tiangolo.com/tutorial/background-tasks/)

SQLite is a reasonable proposed starting point for one machine and low write concurrency; WAL requires local same-host access and still allows only one writer at a time. Use short transactions, a busy timeout, atomic job claiming, and a single-worker concurrency limit. Upgrade to a server database and a distributed queue if multi-host execution becomes necessary. [sqlite](https://www.sqlite.org/wal.html)

Keep the repository, run directories, and local database in the WSL Linux filesystem when using Linux tools; Microsoft recommends this placement over cross-filesystem access for performance. [learn.microsoft](https://learn.microsoft.com/en-us/windows/wsl/filesystems)

### Existing-package adapters

Treat the UI integration as an additional package, not a refactor of proven phases:

```text
control_center/
  ui/                 forms, tables, inspector panels
  api/                submit / inspect / cancel endpoints
  worker/             jobs, leases, process supervision
  adapters/           intake, supervisor, data, pytest
  policies/           stage registry and execution gates
  storage/            jobs, evidence, events, artifact index
  tests/              backend and browser integration tests
```

During preflight, inspect the actual callable signatures and state definitions. The conversation used `accept_request`, `state_from_intake`, and `strategy_supervisor`; do not invent a Data callable or rely on a prior package description as proof of compatibility.

For the MVP, let the UI request execution up to a target, while the backend adapter composes or selects an appropriate tested graph. Preserve the existing minimal supervisor graph and its regression tests.

### Authorization boundary

The earlier supervisor contract was intentionally `plan_only` with `execution_authorized=False`. Adding a Data button must **not** bypass that safeguard by setting a UI checkbox or mutating a hashed plan.

Define a separately tested, versioned authorization adapter before enabling Prepare Data. A proposed execution envelope binds: job ID, source/environment fingerprints, request hash, plan hash, dataset hash, permitted target, allowed paths, resource limits, mode, and expiry. The worker checks the envelope and applicable domain safeguards immediately before execution.

If the existing Data Agent requires authorization inside its own state contract, integrate through that contract explicitly. A control-plane envelope alone is not permission to bypass it. If compatible authorization is not implemented, keep Prepare Data disabled.

Fixture mode and real-data mode must have distinct labels, grants, and output locations. Neither authorizes broker activity. The MVP contains no broker credentials or order-placement capability.

## Events and persistence

Start with **database-backed polling** for run state and log cursors; one-second refresh is a proposed default, not a performance claim. Add Server-Sent Events later without changing the durable event model.

Suggested event fields: `schema_version`, `job_id`, `attempt_id`, monotonic per-attempt `sequence`, UTC timestamp, `stage`, `event_type`, and bounded payload. Store event timestamps in UTC and optionally display Asia/Singapore time in the browser.

LangGraph exposes node state updates through `updates` and application-defined progress through `custom` streaming. Adapt the streaming API supported by the repository's installed version; do not upgrade runtime APIs solely to build the UI. An `updates` event is not a percentage-complete estimate, and a long-running node may need explicit progress events. [docs.langchain](https://docs.langchain.com/oss/python/langgraph/streaming)

Persist normalized events before advertising them to clients. Browser reconnection should replay after a cursor, not rerun work. A log viewer reconnect is not a graph resume.

A database-backed job list is also **not** a LangGraph checkpoint store. True graph resume needs compatible persisted checkpoints and the same execution identity; keep the Resume button disabled until this has been implemented and tested. Streaming checkpoint/task modes also have checkpointer requirements. [docs.langchain](https://docs.langchain.com/oss/python/langgraph/streaming)

### Cancellation and retries

For a local WSL runner, manage each execution in a dedicated process group. On cancellation, stop scheduling downstream stages, signal the group, allow a bounded grace period, and escalate if needed. Python provides subprocess arguments for an explicit working directory, argument lists, and POSIX session creation. [docs.python](https://docs.python.org/3/library/subprocess.html)

Show `cancel_requested` until termination is confirmed. A timeout must terminate descendants, not merely abandon a waiting HTTP request. A dead heartbeat should yield `orphaned` pending reconciliation—not silently requeue potentially running work.

Retry creates a new attempt with its own events and evidence. Reuse published artifacts only after validating identity and hashes. Never append new output into a previous successful attempt or disguise a cache hit as newly executed work.

## Provenance and safety

Record request ID separately from job ID, attempt ID, and any LangGraph thread/checkpoint identifiers. One request may have several executions; these identifiers are not interchangeable.

Each execution record should capture the repository commit plus effective source snapshot, untracked-input policy, interpreter path/version, environment or dependency fingerprint, test selection/configuration, request/spec/snapshot hashes, plan hash, execution scope, and artifact hashes.

Prefer an immutable local execution snapshot. A clean Git worktree alone does not reproduce dirty or untracked source. Either require a clean committed revision or explicitly copy and hash all execution inputs into a frozen workspace. Prevent tests and subsequent execution from observing different source trees. Fixture metadata alone does not establish real-data coverage.

Proposed guardrails:

- Bind services to loopback by default; require authentication and deployment hardening before shared access.
- Enforce session/CSRF and origin protections appropriate to the UI/API deployment. Localhost is not an authentication mechanism.
- Register trusted repository and environment profiles server-side. Do not accept arbitrary shell commands, Python paths, module names, pytest flags, or working directories from form text.
- Launch commands as argument lists with `shell=False`; Python documents shell-related security considerations. [docs.python](https://docs.python.org/3/library/subprocess.html)
- Verify artifact IDs against the run's artifact index and configured roots; never expose arbitrary filesystem downloads.
- Use bounded previews and text escaping. Redact secrets from logs and state views; pass only the necessary environment variables.
- Apply output-size, process-time, memory, and disk limits in the worker's supported isolation mechanism.
- Tests execute repository Python code. Command allowlisting is not a sandbox; do not run untrusted pull requests locally with secrets.
- “No network” requires enforced isolation or an equivalent tested policy; a UI switch or environment variable is not enforcement.
- Do not auto-install dependencies, auto-update source, commit changes, or automatically apply LLM repairs.

## GitHub integration later

Keep local execution usable without GitHub credentials. Start by linking the recorded revision and existing Actions result. Later add explicitly approved workflow dispatch and artifact retrieval; GitHub supports manual workflows through its UI, CLI, or REST API. [docs.github](https://docs.github.com/en/actions/how-tos/manage-workflow-runs)

Store remote run identity and verify code/environment/test fingerprints before using a remote result as evidence. “Latest branch passed” is not evidence for a different local checkout. Manual dispatch also has workflow-file/default-branch requirements that must be accounted for during setup. [docs.github](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)

Do not put a personal access token in browser storage or request JSON. Initially, avoid dispatching untrusted refs or registering a privileged self-hosted WSL runner.

## Incremental build plan

| Milestone | Deliverable | Acceptance criterion |
|---|---|---|
| A: Inspect and register | Inventory real packages, entrypoints, fixture semantics, environment profiles, test commands | Preflight accurately distinguishes available, missing, and incompatible phases |
| B: Tests dashboard | Tests Only jobs, durable history, logs, JUnit parsing, cancellation | Failed/no-collection/timeout cases cannot appear green; browser closure does not cancel execution |
| C: Request and planning | Form → existing intake → supervisor, input/output inspector, lineage | Valid request reaches planned; invalid input never executes supervisor; iteration stays zero |
| D: Authorized Data | Explicit grant adapter, target-specific tests, compatible snapshot, verified publication | Data-ready state appears only after supported authorization and hash-verified artifacts |
| E: Hardening | Fingerprint gating, recovery, cache verification, API/browser tests | Duplicate submit, code change, worker death, tampering, and path traversal behave safely |
| F: Optional integrations | Studio link, GitHub evidence, later agents | Additional capabilities cannot bypass existing gates |

Do not wait for every specialist agent before building the UI. Start with the Tests dashboard, then attach already validated phases. That immediately removes repeated terminal invocations while limiting integration risk.

## UI acceptance tests

1. Submit Tests Only: required suites run; no research stage is executed.
2. Force one required test to fail: the execution target is blocked and its traceback is inspectable.
3. Collect no tests: show a blocked/misconfigured gate rather than success.
4. Skip a required test: do not treat the suite's zero exit code as sufficient evidence.
5. Submit an invalid request: show field errors; supervisor and Data are not called.
6. Run Plan Only: produce planned state; no data artifact or changed authorization appears.
7. Request incompatible instrument/snapshot inputs: reject explicitly without substitution.
8. Request fixture data execution: label all outputs and preserve fixture lineage.
9. Request real-data execution with fixture-only authorization: reject it.
10. Double-click submit: one idempotency key creates one logical job.
11. Refresh or close the browser: worker continues and history reappears on reconnect.
12. Change source or environment after green tests: gate invalidates before execution.
13. Cancel an active job: no downstream stage starts; descendants terminate before cancelled is shown.
14. Kill the worker: stale heartbeat produces an auditable orphaned/recovery state, not success.
15. Tamper with a cached artifact: verification fails; no silent cache reuse.
16. Attempt arbitrary command/path submission: backend rejects it regardless of frontend controls.
17. Leave a stage unimplemented: the UI cannot schedule it and shows why.
18. Complete data preparation: operational success does not imply research acceptance or profitability.

Use API/worker tests for policy and process behavior, and a small browser suite for submission, failure inspection, reconnection, and disabled controls. Playwright's Python assertions can wait for eventual visible state without hard-coded sleeps. [playwright](https://playwright.dev/python/docs/test-assertions)
